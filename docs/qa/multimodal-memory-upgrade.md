# Multimodal memory completion report

Implementation only, based on `main` at `05d99f2`. No production operations were performed.

1. **Unified architecture:** journal passages, private photo derivatives, and queries use the same configured `embeddinggemma-2:440m` model and 768-dimensional semantic space. Source entries and private Drive photos remain authoritative.
2. **Schema:** additive migration `20261021010000_photo_memory` adds `JournalPhotoMemory` and photo freshness fields. Each photo has independent provenance, nullable vector, status/error, and timestamps. Photo deletion cascades to its vector. No approximate vector index is added.
3. **Text client:** existing batched passage/query transport now defaults to EmbeddingGemma 2, preserves passage prompting/chunking, uses `truncate:false`, validates 768 finite numbers, and exposes typed transport/response errors.
4. **Image client:** the same transport accepts Ollama's structured `input: { image: base64 }`. Runtime JPEG/dimension checks reject full-resolution bytes even if caller-supplied dimensions are forged. No separate vision service is introduced.
5. **Query design:** exactly one query embedding is reused in one SQL statement across the two vector sources. Model/version filters prevent mixing incompatible generations.
6. **Text indexing:** existing transactional jobs, source hashes, stale checks, passage splitting, and atomic generation replacement are retained. The worker now requires explicit `JOURNAL_TEXT_INDEXING_ENABLED=true`; startup does not perform a source scan.
7. **Photo indexing:** separate `journal-photo-embedding` queue and worker. Downloads, decode, and inference happen outside database transactions. A short final lock rechecks source state. New attachments enqueue transactionally only when enabled; editing an entry does not queue its historical attachments. Singleton queue policy limits active photo jobs globally to one; automatic retries are disabled.
8. **Preprocessing:** bounded private download, JPEG/PNG validation, EXIF orientation, white transparency flattening, aspect-ratio preservation, no upscaling, maximum 512px longest edge, quality 85, metadata stripping. Existing HEIC/HEIF JPEG representations follow this path. Originals are untouched.
9. **Phone/safety handling:** generated 24 MP and 48 MP images are accepted; 65.61 MP input is explicitly rejected by the default 64,000,000-pixel ceiling. Input bytes default to 10 MiB. Limits and timeouts are centralized. Native decode and timed-out Ollama CPU work are not claimed to be cancellable.
10. **Evidence ranking:** entries rank by their best cosine match, without arbitrary weighting or score addition. The best passage and up to three matching photo references remain attached to each entry. Relevance, recent, and longitudinal modes are preserved.
11. **Luna vision:** at most three photos are privately downloaded and normalized per outbound request. Ownership/source state is checked before and after I/O. Actual JPEG data URLs pass through the existing OpenAI-compatible ChatMock message path. Missing images preserve text replies; the prompt forbids unsupported visual claims.
12. **Follow-ups:** safe photo/entry references are stored in existing turn evidence. The newest retrieval keeps its original within-batch ranking. Follow-ups re-fetch and reauthorize images; image bytes and Drive URLs are stripped from stored evidence.
13. **Controls:** `PHOTO_INDEXING_ENABLED`, `PHOTO_MEMORY_ENABLED`, and `PHOTO_VISION_ENABLED` default off. Disabling retrieval also disables photo fetching/forwarding. Inference failures persist a pause and stop photo work; explicit acknowledgement and worker restart are required. Text work remains separate.
14. **Text rebuild:** `pnpm memory:backfill` defaults to a bounded, owner-scoped dry run. Explicit `--enqueue` queues noncurrent entries. Entry IDs, dates, page limits, status summaries, and resumable cursors are supported.
15. **Photo backfill:** `pnpm memory:photos:backfill` offers the same controls plus photo IDs. It requires the indexing flag before enqueueing. No migration/startup/flag change scans or enqueues historical photos.
16. **Production restrictions:** neither production backfill ran. No production database, Drive data, secrets, deployment, Ollama installation/runtime, or networking was changed.
17. **Deprecation:** old vectors are rebuilt from source, never converted. Atomic text replacement removes the old per-entry generation. The old installed model and legacy environment setting can be removed after a separately validated cutover; no permanent dual-model retrieval exists.
